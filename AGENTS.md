# Правила проекта Horde Muncher

- Соблюдать `docs/development/task-workflow.md`: по умолчанию работать в общей ветке `main`, учитывать параллельную работу других агентов и фиксировать завершённые наборы изменений коммитами после подходящих проверок.

- При создании и изменении C# кода читать и соблюдать `docs/development/csharp-style.md` и `docs/development/clear-names.md`. Существующие нарушения не разрешают новые нарушения.
- UI строить по MVP. View пассивна: отображает переданное состояние и сообщает о пользовательских действиях. Presenter работает с обычными C#-контрактами состояния и команд, без World, Entity и RPC. Доступ к клиентскому ECS и отправку RPC держать в отдельном мосте. Контексты локальных игроков передавать явно из сессии, не искать их в UI через World.All или имя мира.
- Для пассивных экранов без действий пользователя достаточно Presenter, обновляющего разметку; не вводить отдельный класс View и интерфейс только ради шаблона.
- Действия с удержанием всегда сопровождать видимым прогрессом от начала до завершения; при отпускании или отмене сбрасывать индикатор. Для вступления в лобби показывать круговой прогресс отдельно для каждого удерживающего игрока, рядом с его подписью.
- Не добавлять ECS-компоненты для элементов интерфейса. Игровое состояние остаётся в ECS; UI получает его через адаптер.
- Изменять стиль существующего кода в рамках затронутого участка, без несогласованного массового переформатирования.
- Не добавлять DI-пакет только ради атрибута Inject; рекомендации по внедрению применять с имеющимися зависимостями проекта.

- На этапе прототипа приоритет — скорость разработки. Соблюдать `docs/development/prototype-workflow.md`: проверять компиляцию и по необходимости запускать EditMode-тесты. Не запускать Play Mode и не делать игровые скриншоты без явного запроса пользователя.
- Работать через код, файлы, логи и программные инструменты. Не смотреть на экран, не снимать и не анализировать скриншоты и не использовать визуальное управление приложениями без явного запроса пользователя: это расходует лишние токены. О визуальных проблемах пользователь сообщит сам.
- Тесты добавлять точечно для существенных рисков или по прямому запросу, без широкого покрытия простых изменений. Использовать Unity Test Framework и независимые сценарии. Не добавлять новые меню Verify или ручные проверочные команды вместо тестов.

- Названия должны быть понятными человеку при чтении и отражать конкретный смысл. События разных действий пользователя называть отдельно; смысл аргументов должен быть явным.

- Не писать комментарии в коде, включая XML-документацию и закомментированный код. Код должен читаться просто за счёт понятных названий, небольших методов и ясной структуры. Если участок требует пояснения, упростить его или выделить действие с конкретным названием.
